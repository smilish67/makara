# Makara

공모전과 프로젝트 경험을 축적해 다음 컨셉 대화와 제작을 돕는다. Honcho는 사용자 선호·선택 이유·판단 변화의 추론 계층이고, Markdown 위키는 프로젝트 목적·결정·조사·진행 상태·재사용 경험이다. 추론은 확정 사실이 아니다.

## 연결과 조회

`makara_status`로 접근 범위를 확인하고 요청에 맞는 scope만 `makara_context`로 조회한다. 필요하면 `makara_memory`에 구체적인 질문을 보낸다. 모든 개인 기억을 무조건 주입하지 않는다. MCP 이름 앞에 플러그인 namespace가 붙을 수 있다.

공모전 간 비교 요청이면 관련 프로젝트들의 context와 memory를 각각 조회해 근거를 비교한다. 현재 기억은 scope별로 분리되므로 모든 프로젝트의 판단이 자동으로 me에 통합됐다고 주장하지 않는다.

MCP가 목록에 없지만 로컬 실행이 가능하면 이 스킬 폴더 기준 `../../scripts/bridge.py`를 사용한다:

```sh
python3 <plugin-root>/scripts/bridge.py status
python3 <plugin-root>/scripts/bridge.py capture-status
```

다른 API 동작은 `python3 <plugin-root>/scripts/bridge.py request <action>`의 표준입력에 JSON을 전달한다. 토큰을 읽어 출력하거나 위키에 넣지 않는다. 연결 실패를 저장 성공으로 표현하지 않는다. 웹/클라우드 채팅은 로컬 실행 또는 연결된 MCP가 실제로 있어야 사용 가능하다.

## 컨셉 설계와 첫 시안

- 공모전·개인 프로젝트에서 선택에 따라 결과가 달라지는 순간에는 현재 세션의 설계자가 관련 근거를 조회한다. 출처와 당시 조건을 밝히고, 이번에도 적용할지 불확실하면 구체적인 사용 장면으로 묻는다. 사양이 정해진 일반 구현에서는 해당 작업에 필요한 맥락만 쓴다.
- 사용자가 고를 만한 안을 먼저 제시한 뒤 확장안을 설명한다. 각 안의 의도와 확인할 장면을 먼저 밝히고, 핵심 경험을 직접 해볼 수 있는 작은 시안이나 컴포넌트를 비교해 확장·조합·중단을 판단하게 한다. 처음 쓰는 사람이 무엇을 생각할지에 대한 예상과 실제 관찰을 구분한다.
- 위임할 때는 사용 가능한 실행 도구·모델·인증 프로필을 선택한다. 구현자에게 선택한 컨셉, 시안 범위, 직접 해볼 행동과 확인 기준을 전달한다. 설계·구현 모델은 교체 가능하며 기억 처리 모델은 독립적으로 운영한다. 인계 내용은 수신 제공자의 허용 범위에 맞춘다.
- 사용자가 정리를 요청하면 과거 근거, 이번 질문과 답, 실제 시안에서 달라진 부분, 사용자가 살리거나 버린 부분과 그 이유를 연결한다. 다른 프로젝트에 적용할 때는 조건과 예외를 밝힌다. 한 번의 반응이나 구현 실패로 보편적인 취향을 단정하지 않는다.

## 수집과 문서 갱신의 구분

- 플러그인이 활성화된 로컬 Codex 세션에서는 훅이 사용자 입력·최종 응답을 수집한다. 서버는 프로젝트를 구분하고 Honcho로 전달한다. 도구 출력·첨부파일 본문은 자동 수집 대상이 아니다.
- **위키와 me/now는 사용자가 요청했을 때만 갱신한다.** “오늘 작업 마무리해서 마카라 업데이트”, “이 단위 정리해줘” 또는 명시적인 문서 수정 요청이 해당한다. 평소 대화·작업 완료·Stop 이벤트는 갱신 요청이 아니다.
- “이전 판단을 알려줘”는 조회 요청이다. 읽은 김에 위키를 수정하지 않는다.
- 캡처 활성화는 다른 제공자에게 공개하거나 환경 설정을 임의 변경할 권한이 아니다. 새 범위는 상태에서 확인하고, 허용되지 않은 자료를 복사해 권한을 우회하지 않는다.

## 요청받은 업데이트

1. 대상 프로젝트와 작업 기간/단위를 현재 대화에서 파악한다. 불명확할 때만 확인한다. 기존 문서와 허용된 `makara_source_feed`를 읽고, 잘린 출처는 `makara_inspect_source`로 확인한다.
2. 현재 채팅이 자동 수집되지 않았다면, 사용자가 정리하도록 지정한 작업 결과만 source로 저장한다. 실제 발언 시점과 기록 시점을 분리한다. 응답이 queued이면 아직 저장 완료가 아니다.
3. 컨셉 후보·선택/기각 이유·조사로 바뀐 판단·실행 결과·재사용 자산을 정리한다. 에이전트 제안과 사용자의 확정 결정을 구분한다. 완료 보고만 있고 증거를 읽지 않았다면 검증 완료로 바꾸지 않는다.
4. 프로젝트의 `overview`, `decisions`, `state`, `knowledge/...` 중 필요한 문서만 갱신한다. 기존 문서를 읽은 최신 version과 출처 IDs로 `makara_propose`한다. 충돌 시 재조회·비교하고 덮어쓰지 않는다. 이미 요청받은 갱신에 별도 승인을 반복 요구하지 않는다.
5. `me/now`는 개인 전체의 현재 집중 대상·가까운 마감·제약·프로젝트 링크만 짧게 유지한다. 사용자가 명시한 우선순위 변화가 없으면 작업량만으로 최우선 목표를 바꾸지 않는다. 마감 경과만으로 완료·중단을 추정하지 않는다. 프로젝트 출처를 직접 me 문서에 붙이지 말고, 필요한 개인 현황 근거를 허용된 me source로 별도 기록한다.
6. 저장 후 재조회하고 갱신 문서 링크·근거·미확인 사항을 보고한다. 모든 대화를 정리했다고 주장하려면 실제 검토 범위를 확인한다.

잘못된 원문의 정정·삭제는 명시적 요청에 따라 처리한다. 일반 위키 편집에 기억 삭제를 사용하지 않는다. Honcho가 생성 중이면 기존 위키로 진행하고 추론 완료를 기다리는 반복 조회를 하지 않는다.
